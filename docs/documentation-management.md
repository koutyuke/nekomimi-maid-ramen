# ドキュメント管理

この文書は、人間とAgentが同じ規則で文書を追加・更新できるように、正本、ID、形式、更新手順を定める。人間が短時間で内容を理解できることを最優先にし、構造化は検索と参照に必要な範囲に限定する。

## 三つの正本

| 層         | 答える問い                     | 書くもの                                             | 書かないもの                     |
| ---------- | ------------------------------ | ---------------------------------------------------- | -------------------------------- |
| `product/` | 何を、誰のために、なぜ作るか   | 目的、利用者、体験、ユースケース、共通語彙           | 技術要件、画面項目、状態遷移     |
| `meta/`    | 何を満たすか、何を決めるか     | 要件、判断、未決事項、根拠、機能計画、提供範囲       | 詳細な操作や受け入れ手順         |
| `specs/`   | システムと運用はどう振る舞うか | 操作、状態、データ、画面、例外、品質条件、受け入れ例 | 背景、長い判断理由、検討中の機能 |

仕様は「画面」「データ」「機能」「品質」のような成果物・技術レイヤーで分けない。関係する情報を一か所で読めるよう、業務能力・ドメインによる縦割りで管理する。

## 業務領域

| コード | 領域                | 対象                                                     |
| ------ | ------------------- | -------------------------------------------------------- |
| `VIS`  | Visitor Information | 出店情報、メニュー、スポンサー情報                       |
| `SAL`  | Sales               | 注文受付、金額計算、現金会計、注文確定                   |
| `INV`  | Inventory           | 在庫、販売可否、在庫の減算と復元                         |
| `KIT`  | Kitchen             | 調理対象と調理状況                                       |
| `HAND` | Handoff             | 注文番号の照合と受け渡し                                 |
| `OPS`  | Operations          | 開店準備、障害対応、閉店処理                             |
| `SYS`  | System-wide         | 複数領域へ同じ条件で作用する品質、セキュリティ、利用環境 |

`SYS`は共通事項の置き場として安易に使わず、一つの業務領域へ所属できない内容に限定する。

## 形式と配置

| 情報     | 形式                         | 配置                              |
| -------- | ---------------------------- | --------------------------------- |
| 要件     | TOML                         | `meta/requirements/{domain}.toml` |
| 提供範囲 | TOML                         | `meta/releases/PROFILE-*.toml`    |
| 判断     | Markdown + YAML Front Matter | `meta/decisions/DEC-*.md`         |
| 未決事項 | Markdown + YAML Front Matter | `meta/questions/Q-*.md`           |
| 根拠     | Markdown + YAML Front Matter | `meta/evidence/EVID-*.md`         |
| 機能計画 | Markdown + YAML Front Matter | `meta/plans/PLAN-*.md`            |
| 仕様     | Markdown + YAML Front Matter | `specs/{domain}.md`               |

Markdownのファイル名は、IDと短い英語名を組み合わせる。例は`Q-SAL-001-order-confirmation-timing.md`である。作成後は、タイトル変更だけを理由にファイル名を変更しない。

## ID

| 形式                 | 意味                     | 例                |
| -------------------- | ------------------------ | ----------------- |
| `REQ-{領域}-{番号}`  | 必要な結果と制約         | `REQ-SAL-001`     |
| `SPEC-{領域}-{番号}` | 個別に検証できる振る舞い | `SPEC-SAL-001`    |
| `DEC-{領域}-{番号}`  | 現在有効な判断           | `DEC-SAL-001`     |
| `Q-{領域}-{番号}`    | 未決事項                 | `Q-SAL-001`       |
| `PLAN-{領域}-{番号}` | 検討中の機能計画         | `PLAN-SAL-001`    |
| `EVID-{種別}-{番号}` | 調査・実測などの根拠     | `EVID-USER-001`   |
| `PROFILE-{名前}`     | 提供範囲                 | `PROFILE-INITIAL` |

番号は3桁とし、情報種別と領域の組み合わせごとに採番する。削除したIDは再利用せず、削除済みIDの一覧も作らない。必要な履歴はGitで確認する。

## 要件TOML

一つの業務領域を一つのファイルにまとめ、`[[requirements]]`へ要件を追加する。

```toml
schema = "requirement-set"
domain = "sales"
domain_code = "SAL"

[[requirements]]
id = "REQ-SAL-001"
title = "注文候補を入力できる"
kind = "functional"
statement = "会計担当者は、来場者から聞いた商品と個数を注文候補として入力・修正できる。"
reason = "聞き取った注文内容を、調理担当者へ正確に共有するため。"
priority = "must"
status = "draft"
specs = ["SPEC-SAL-001"]
depends_on = []
sources = []
```

| 項目       | 許可値                                |
| ---------- | ------------------------------------- |
| `kind`     | `functional`、`quality`、`constraint` |
| `priority` | `must`、`should`、`could`             |
| `status`   | `draft`、`accepted`                   |

`specs`は、要件を具体化する仕様IDの正本である。`depends_on`は前提となる要件ID、`sources`は判断または根拠のIDを記載する。詳細な操作、例外、受け入れ例はTOMLへ書かない。

## YAML Front Matter

`schema`、`id`、`title`を単一記録の共通項目とし、文書種類に応じて`domain`や参照IDを追加する。複数の`SPEC-*`を含む仕様書は文書自体の`id`を持たない。

領域固有の項目は、検索・判断・検査に使う場合だけ追加する。項目名は`snake_case`とし、同じ領域かつ同じ`schema`では意味を統一する。本文で十分な説明はFront Matterへ重複させない。

## 要件と仕様の対応

要件TOMLは`specs`で仕様IDを参照し、仕様の各節は`関連要件`として要件IDを示す。

```markdown
## SPEC-SAL-001 注文候補を作成する

関連要件: `REQ-SAL-001`
```

要件TOMLの`specs`を正本とし、仕様側の参照は読者がその場で目的を確認するために記載する。更新時は両方向が一致することを確認する。

## テンプレート

新規作成では格納先にあるテンプレートを複製し、不要な項目と節を削除する。必要な情報がある場合は節を追加できるが、同じ領域内では大まかな構成と項目の意味を揃える。

| 対象     | テンプレート                                 |
| -------- | -------------------------------------------- |
| 要件     | `meta/requirements/requirement-set.tpl.toml` |
| 提供範囲 | `meta/releases/profile.tpl.toml`             |
| 判断     | `meta/decisions/decision.tpl.md`             |
| 未決事項 | `meta/questions/question.tpl.md`             |
| 根拠     | `meta/evidence/evidence.tpl.md`              |
| 機能計画 | `meta/plans/plan.tpl.md`                     |
| 仕様     | `specs/spec.tpl.md`                          |

テンプレートは実データのID検査対象に含めない。

## 更新フロー

### 新しい要件を追加する

1. 対象となる業務領域を決める。
2. `meta/requirements/{domain}.toml`へ`REQ-*`を追加する。
3. `specs/{domain}.md`へ、対応する`SPEC-*`を追加する。
4. 要件の`specs`と仕様の`関連要件`を相互に参照させる。
5. 必要な判断、根拠、未決事項を追加する。
6. 提供範囲へ含める場合は`PROFILE-*`へ要件IDを追加する。
7. ID、参照、リンク、現在の文書との矛盾を確認する。

### 未決事項を解決する

1. 解決内容を要件と仕様へ反映する。
2. 現在も判断理由が必要な場合だけ`DEC-*`を作成する。
3. `Q-*`への参照を取り除き、`Q-*`を削除する。
4. `PROFILE-*`の`blocking_questions`を更新する。

### 機能計画を採用する

1. `PLAN-*`の内容を要件と仕様へ移す。
2. 必要な`REQ-*`と`SPEC-*`を作成する。
3. 対象となる`PROFILE-*`を更新する。
4. `PLAN-*`を削除する。

### 要件や仕様を変更・削除する

1. 関連する要件、仕様、判断、根拠、未決事項、提供範囲を検索する。
2. すべてを現在の正しい状態へ更新する。
3. 不要になった文書と参照を削除する。
4. 変更前の説明や削除理由を本文へ残さない。

## 手動確認

検査スクリプトは、プロジェクトの実装言語が決まるまで作成しない。更新時は次を手動で確認する。

- TOMLとYAML Front Matterの構文が正しい。
- IDの種類、領域コード、3桁連番が規則に合う。
- IDが重複していない。
- 参照するIDとローカルリンクが存在する。
- 要件の`specs`と仕様の`関連要件`が一致する。
- `kind`、`priority`、`status`が許可値に含まれる。
- 仕様が業務領域でまとまり、技術レイヤーごとに分散していない。
- 現在の正しい状態だけが残り、編集経緯や不要な計画が混ざっていない。
