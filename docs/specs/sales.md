# 注文・会計仕様

## 結論と対象範囲

来場者が注文兼会計口で商品と個数を伝え、会計担当者が注文候補として画面へ入力する。注文候補は、会計担当者が確定操作を行うまで正式な注文ではない。

会計担当者は、現金とお釣りのやり取りを終えてから注文を確定する。確定前は正式な注文も在庫の変更も発生しないため、確定に失敗した場合は現金を返してやり直せる。

## 関係者

| 関係者     | 役割                                                       |
| ---------- | ---------------------------------------------------------- |
| 来場者     | 注文する商品と個数を会計担当者へ伝え、内容と金額を確認する |
| 会計担当者 | 注文候補を入力・修正し、在庫と金額を確認して注文を確定する |
| システム   | 金額と販売可否を算出し、確定した注文を保存する             |

## 画面と管理データ

Staff以上の担当者は、スタッフページの「注文・会計」から`/sales`を開く。スマートフォンの縦向きで操作できる。

注文・会計画面は、商品と個数の入力・修正、現在の販売可否、小計、合計金額、受取金額、お釣り、確定結果を扱う。

確定注文には、注文番号、注文明細、確定時の価格、合計金額、明細ごとの調理状況、受け渡し日時を保持する。注文全体の調理状況は明細から算出し、受け渡し状況は受け渡し日時の有無で判定する。確定後も適用した価格と合計金額を再現できる必要がある。

## 通常時の流れ

| 手順 | 主体                 | 作業                               | 完了状態                                             |
| ---- | -------------------- | ---------------------------------- | ---------------------------------------------------- |
| 1    | 来場者               | 商品と個数を会計担当者へ伝える     | 会計担当者が入力を開始できる                         |
| 2    | 会計担当者           | 商品と個数を入力する               | 注文候補が表示され、正式な注文と在庫は未変更         |
| 3    | システム             | 小計、合計金額、販売可否を表示する | 内容、金額、販売可否を確認できる                     |
| 4    | 会計担当者           | 入力内容と現在の在庫を確認する     | 販売可否を判断できる                                 |
| 5    | 会計担当者           | 現金を受け取り、お釣りを渡す       | 会計が完了している                                   |
| 6    | 会計担当者・システム | 確定操作を行い、注文番号を発行する | 注文が保存され、在庫が減り、調理担当者から参照できる |
| 7    | 会計担当者           | 注文番号を紙へ書いて渡す           | 来場者が注文番号を受け取っている                     |

手順6で在庫不足により確定できなかった場合は、受け取った現金を返し、手順2から入力し直す。

## SPEC-SAL-001 注文候補を入力・修正する

関連要件: `REQ-SAL-001`

商品一覧の各行に「−」「選択数 / 最大10個」「＋」を置き、タップだけで個数を変更できる。0個は未選択を表し、1個以上にすると注文候補へ加わる。0個へ戻すと注文候補から外れる。商品一覧と注文候補は同じ行で扱い、選択中の商品には小計を表示する。

一つの注文に含められる商品の種類数は制限しない。商品ごとの個数は1個以上10個以下とし、範囲外の個数は受け付けない。同じ商品を複数の明細へ分けることはできず、個数の変更で表す。

### 受け入れ例

1. 会計担当者が商品と個数を入力する。
2. 商品を追加し、別商品の個数を変更する。
3. 変更後の商品と個数が注文候補として表示される。

## SPEC-SAL-002 注文候補で注文と在庫を変更しない

関連要件: `REQ-SAL-002`

注文候補の作成、追加、削除、個数変更では、正式な注文を作成せず、在庫も確保・減算しない。調理担当者へ共有するのは確定した注文だけである。

### 受け入れ例

1. 注文候補を作成して内容を変更する。
2. 確定せずに画面を離れる。
3. 正式な注文件数、在庫、調理対象が変化していない。

## SPEC-SAL-003 小計と合計金額を算出する

関連要件: `REQ-SAL-003`

注文候補に含まれる各商品の現在の価格と個数から小計を算出し、その合計を表示する。小数、負数、1個未満または10個を超える個数は受け付けない。

### 受け入れ例

1. 価格と個数が異なる複数の商品を入力する。
2. 商品ごとの小計と合計金額を確認する。
3. 表示金額が価格と個数から算出した金額に一致する。

## SPEC-SAL-004 受取金額からお釣りを算出する

関連要件: `REQ-SAL-004`

受取金額が合計金額以上の場合は差額をお釣りとして表示する。合計金額未満または数値として扱えない入力では、正しい会計結果として扱わず、注文を確定できない。

受取金額は100円単位とし、末尾の`00`を固定して大きく表示する。画面内のテンキーと端末のキーボードで百円より上の桁を入力でき、1桁削除とクリアができる。`+100円`、`+500円`、`+1,000円`、`+5,000円`、`+10,000円`のボタンは受取金額へ加算する。

### 受け入れ例

1. 合計金額以上の受取金額を入力する。
2. 受取金額と合計金額の差額がお釣りとして表示される。

## SPEC-SAL-005 注文を一度だけ確定する

関連要件: `REQ-SAL-005`、`REQ-INV-002`、`REQ-INV-003`

「注文を確定」を押すと、商品・個数・合計金額・受取金額・お釣りを示す確認ダイアログを開く。この時点では確定要求を送らない。「入力に戻る」または閉じる操作で修正へ戻り、「はい、確定する」で確定要求を送る。

確定操作では、現在の在庫による最終判定に成功した場合だけ、注文を一件作成し、重複しない注文番号を発行する。確定した注文だけを調理担当者へ共有する。

同じ操作の連打や再送で同じ注文を複数作成しない。会計担当者の端末は確定操作ごとに要求識別子を生成し、再送では同じ識別子を使う。確定済みの識別子で確定を求められた場合は、新しい注文を作らず、確定済みの注文をそのまま返す。

通信失敗で確定結果が不明な間は注文内容を固定し、「同じ注文の結果を再確認」で同じ要求を再送する。結果が判明するまで返金や別の注文入力を行わず、画面を閉じたり再読み込みしたりしない。ただし、紙運用への切り替えが宣言された場合は、[`SPEC-OPS-002`](operations.md)に従って返金し、復帰前に確定結果を照合する。要求識別子は画面を開いている間だけ保持するため、画面を失った場合は管理者と確定状況を確認してから対応する。

確定成功時はダイアログに注文番号、確定した商品・個数・小計、合計、受取金額、お釣りを表示する。注文番号を紙へ書いて渡し、「番号を控えて次の注文」またはダイアログを閉じる操作で入力を空にする。直前の確定注文1件をメモリに保持し、「前回の注文を確認」で再表示できる。再表示しても入力中の注文候補は変化しない。画面を離れたり再読み込みしたりすると前回の注文は失われる。入力時と確定時の金額が異なる場合は、表示された確定金額に合わせて差額を精算する。

在庫の減算と失敗時の整合性は[`inventory.md`](inventory.md)で定義する。採番と二重確定の防ぎ方は[`DEC-SAL-001`](../meta/decisions/DEC-SAL-001-order-confirmation-persistence.md)で定める。

### 受け入れ例

1. 販売可能な注文候補を作成する。
2. 会計担当者が確定操作を行う。
3. 注文が一件だけ作成され、注文番号が表示され、調理担当者から確認できる。
4. 同じ確定操作を再送しても注文が増えない。

## SPEC-SAL-006 確定した注文を取り消す

関連要件: `REQ-SAL-006`

Staff以上のロールを持つ担当者は、未取消・未受け渡しで、完成した明細が一つもない確定注文を取り消せる。ドリンクを含め、1明細でも完成していれば取り消せない。未調理と調理中の明細だけを含む注文は取り消せる。確定後の内容変更はできない。商品や個数を間違えた場合は、取消条件を満たす注文を取り消してから入力し直す。

取り消しでは、注文明細の数量だけ在庫を戻し、注文を取り消し済みにする。取り消し済みの注文は、調理対象にも受け渡し対象にもならず、調理状況の更新と受け渡しの完了を受け付けない。取り消した担当者と日時を記録する。返金は現金で行い、システムでは扱わない。

スタッフページの「注文管理」から`/order-management`を開き、営業日を選んで全状態の注文を確認する。初期表示は日本時間の当日とする。注文番号・商品と個数・状態・操作をリストで表示し、取消済み・完成・受け渡し済みも残して取消不可の理由を示す。接続中の表示はタイトルの横に置き、接続状態が変わっても一覧の位置を動かさない。

APIは営業日ごとの注文を全件返す。注文管理では`GET /staff/orders?businessDate=:businessDate&includeCancelled=true`で取消済みも取得し、画面側で注文番号の降順に20件ずつ表示する。`includeCancelled`を省略または`false`とした場合は取消済みを除外し、調理・受け渡し画面の取得範囲を保つ。日付変更では1ページ目へ戻り、自動更新ではページ番号を維持する。ページ数が減った場合は最後のページへ合わせる。

「取り消す」で注文番号・営業日・商品と個数、在庫が戻ること、元に戻せないことを示す確認を開く。「はい、取り消す」で承認した場合だけ送信する。確認中に対象が取消不可となった場合は確認を閉じる。自動更新で表示順が変わっても、確認対象を別の注文へ差し替えない。

`POST /staff/orders/:id/cancel`はStaff以上に限り、保存時にも権限と取消条件を確認する。在庫復元と取消記録を一つのバッチで保存し、途中の失敗では全体を取り消す。成功時は取消日時と担当者IDを返す。取消条件不成立・存在しない注文・保存時の権限喪失は`409`、入口で権限が不足する場合は`403`を返す。同時操作や再送で在庫を二重に戻さず、取消記録を上書きしない。完成操作と取消操作が競合した場合は、先に保存が成立した操作だけを成功させる。

保存後は注文と在庫の変更をスタッフ画面へ通知する。一覧取得・変更照合の失敗中と取消処理中は取消操作を止める。競合や通信失敗では自動再送せず一覧を再取得し、対象の状態を確認してから再試行する。返金の要否は現場で確認し、通信失敗だけを理由に重ねて返金しない。

### 受け入れ例

1. Staff・Admin・Ownerが未調理または調理中の注文を取り消すと、取消記録と全明細の在庫復元が一度だけ成立する。
2. ラーメン・サイド・ドリンクのいずれか1明細でも完成した注文と、受け渡し済みの注文では取消が成立せず、在庫も変わらない。
3. None・未認証・保存前にStaff以上の権限を失った担当者による取消は成立しない。
4. 取消済み注文は注文管理に残り、調理・受け渡し画面からは除外される。調理更新と受け渡し完了も成立しない。
5. 同時取消と再送でも一度だけ在庫が戻る。取消と完成を同時に実行しても、両方が成立しない。
6. 在庫復元または取消記録の途中で失敗すると、注文・全在庫・変更リビジョンが操作前の状態を保つ。
7. 確認をキャンセルしても注文は変わらず、承認した場合だけ取り消される。他端末で対象の明細が完成すると確認が閉じる。
8. 21件以上の注文が新しい順に20件ずつ表示され、自動更新でページ番号が変わらない。日付を変更すると1ページ目へ戻る。
