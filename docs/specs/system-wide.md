# システム共通仕様

## 現在の状態

認証とロールによる制限、および`SPEC-SYS-008`のロール付与・剥奪操作は実装済みである。

## 品質を測定する条件

性能試験は、通常時に10分間で6件、ピーク時に10分間で20件の注文を確定する負荷と、スタッフ10人、最大7台の同時利用を想定して行う。通常時とピーク時は別の10分間として測定する。端末自体の故障やモバイル回線の切断は、システムの応答時間と停止時間に含めない。

## 対応環境

来場者とスタッフは、いずれも自分のスマートフォンから利用する。専用端末は用意しない。

| 項目         | 対応範囲                                     |
| ------------ | -------------------------------------------- |
| 端末         | スマートフォン                               |
| ブラウザー   | iOSのSafari、AndroidのChrome。いずれも最新版 |
| 画面         | スマートフォンの縦向き                       |
| ネットワーク | 各利用者のモバイル回線                       |
| 電源         | 役割ごとにモバイルバッテリーを用意する       |

校内Wi-Fiと予備回線は使わない。回線が各利用者に分散するため、一つの回線障害で全担当者が同時に利用できなくなることはない。ただし電波が届きにくい場所では個別に利用できなくなる。

予備端末は用意しない。端末が故障した場合は、別のスマートフォンから同じGoogleアカウントでログインし直して利用を再開できる。

スタッフのログインにはGoogleへ到達できる通信が必要である。営業中の認証失敗を避けるため、ログインは開店前に済ませる。

## SPEC-SYS-001 営業時間中の利用可能性を測定する

関連要件: `REQ-SYS-001`

10時から16時までの営業時間を対象に、異なるモバイル回線を使う会計端末2台から同時に注文を確定できなかった時間をシステムの停止として記録する。1台だけの端末故障または回線切断は含めない。停止は各日1回以下、1回5分以下、2日間の合計10分以下とする。営業時間中に計画停止は行わない。

### 受け入れ例

1. リハーサルまたは本番で、注文を確定できなかった開始時刻と復旧時刻を記録する。
2. 各日の停止回数と1回ごとの停止時間を求める。
3. 各日1回以下、1回5分以下、2日間の合計10分以下であることを確認する。

## SPEC-SYS-002 障害後の注文と在庫を照合する

関連要件: `REQ-SYS-002`、`REQ-INV-003`、`REQ-OPS-002`

通信断または再起動の後も、確定済み注文と在庫の一方だけが変更された状態を残さない。復旧時は注文、在庫、処理結果を照合できるようにする。

### 受け入れ例

1. 注文確定処理中に通信断と再起動を発生させる。
2. 復旧後に注文と在庫を確認する。
3. 注文の有無と在庫の減算結果が一致し、同じ操作の再実行で重複注文が作られない。

## SPEC-SYS-003 注文確定の応答時間を測定する

関連要件: `REQ-SYS-003`

最大7台を同時利用し、10分間で20件の注文を確定する。注文確定操作から成功または失敗の結果表示までを測定し、95%を2秒以内、すべてを5秒以内に表示する。

## SPEC-SYS-004 スタッフ画面への反映時間と復旧時間を測定する

関連要件: `REQ-SYS-004`、`REQ-KIT-001`

スタッフ最大7台の同時利用で、D1の保存確定から該当画面の表示更新までを測定する。注文画面の在庫残数と、調理・受け渡し画面の注文状態を対象とし、通常時は95%を3秒以内、すべてを10秒以内に反映する。

変更通知に失敗した場合は、WebSocketが接続したままでも30秒ごとの照合で検出し、保存確定から35秒以内に回復する。回線断と画面休止中は測定から除外し、通信または画面の復帰時は即座に再取得を始める。

通常時と通知失敗時は別々に測定する。ローカルの複数接続試験で復旧処理を確認し、配備後にiOSのSafariとAndroidのChromeからモバイル回線を使って性能を受け入れ判定する。ローカル試験だけで実機の性能条件を満たしたとは扱わない。

## SPEC-SYS-005 会計操作の使いやすさを確認する

関連要件: `REQ-SYS-005`、`REQ-SAL-001`、`REQ-SAL-005`

会計担当候補者5人が、説明や介助を受けずに商品と個数の入力から注文確定までを各3回行う。15件すべてで商品、個数、金額を正しく確定し、各操作を90秒以内に完了する。商品、個数または金額を誤って確定した場合は不合格とする。

公開画面とスタッフ画面は[WCAG 2.2](https://www.w3.org/TR/WCAG22/)の適合レベルAAを満たす。本文は16 CSSピクセル以上、操作対象は44×44 CSSピクセル以上とする。売り切れ、エラー、処理中、業務状態を色だけに依存せず表示し、200%に拡大しても内容と機能を失わない。すべての操作をキーボードでも実行でき、操作対象の名前と状態変更を読み上げソフトから確認できるようにする。

## SPEC-SYS-006 更新操作を許可された担当者に限定する

関連要件: `REQ-SYS-006`

注文、在庫、調理状況、受け渡し状況を更新する操作は、許可された担当者だけが実行できる。

スタッフ画面は学校のGoogleアカウントで認証し、`gm.ibaraki-ct.ac.jp`ドメイン以外のアカウントは受け付けない。来場者向けの公開ページは認証を要求しない。

スタッフのトップ(`/`)では未認証時にログインを案内する。管理・会計・調理画面を直接開いた場合はセッションを確認し、未認証なら業務データを取得せずトップへ移動する。通信失敗では移動せず、再試行を案内する。認証済みで必要なロールがない場合は権限不足を表示する。

同じドメインであってもログインできるだけでは業務を操作できない。操作の可否はロールで決まり、設定で固定したOwnerを除き初回ログイン時のロールはNoneである。

ログインの入口は`/`である。未ログインならGoogleログインを案内し、Noneなら管理者への権限付与依頼を案内する。ログイン状態の確認とログアウトはNoneでも行えるが、業務操作は行えない。

セッションはログインから12時間有効であり、操作による延長はしない。期限切れなら再ログインする。ログアウトするとその端末のセッションを失効させる。別端末のセッションは維持する。更新要求ではセッションと現在のロールに加え、許可された画面からの送信元であることを確認する。

| ロール | 実行できる操作                                                             |
| ------ | -------------------------------------------------------------------------- |
| Owner  | Adminの全操作とAdminの付与・剥奪。自身のロールは設定で固定                 |
| Admin  | Staffの全操作、在庫の修正、確定した注文の訂正と取り消し、Staffの付与と剥奪 |
| Staff  | 注文の入力と確定、調理状況の更新、受け渡しの完了                           |
| None   | 公開ページの閲覧のみ                                                       |

ロールは業務役割と分ける。会計、調理、受け渡しという業務役割は画面の分かれ方であり、Staffはいずれの画面も利用できる。当日のシフト変更で担当が入れ替わっても、ロールを変更する必要はない。

アカウントを利用できなくなった場合や、ロールを誤って失った場合は、Ownerが再付与する。

### 受け入れ例

1. Owner、Admin、Staff、None、対象ドメイン外のアカウントで各操作を試みる。
2. ロールに応じた操作だけが成立する。
3. Noneと対象ドメイン外のアカウントによる更新は一件も成立しない。

## SPEC-SYS-007 不要な個人情報を収集しない

関連要件: `REQ-SYS-007`

現在の注文、調理、受け渡しでは、来場者の氏名、連絡先、アカウントを収集しない。

スタッフのプロフィールはメールアドレスと表示名に限る。認証とロール管理のため、Googleの不変識別子(`sub`)、アプリ内の利用者ID、ロール、メール確認状態、登録・更新日時、セッションの識別子と有効期限も保持する。Googleのアクセストークン・リフレッシュトークン・IDトークン、プロフィール画像、IPアドレス、User-Agentは保存しない。ログイン途中の照合情報は有効期限付きで保持する。これらの保持期間と削除は`Q-OPS-003`で決定する。

端末識別子、アクセスログ、分析サービスなどで個人を識別し得る情報を扱う場合は、収集前に目的、項目、同意、閲覧権限、保持期間、削除方法を要件として定義する。

## SPEC-SYS-008 ロールを付与・剥奪する

関連要件: `REQ-SYS-008`

OwnerとAdminは、管理ページ(`/admin`)で、ログインしたことがある利用者の名前、メールアドレス、現在のロールを一覧表で確認できる。StaffとNoneには`/`から管理ページへの導線を表示せず、管理ページの閲覧、一覧取得、ロール変更も許可しない。

一覧はOwner、Admin、Staff、Noneの順に並べる。現在のロールはロール名を含むバッジで表示し、色だけに依存せず識別できるようにする。

Ownerは他人のAdmin・Staff・Noneを相互に変更できる。Adminは他人のNoneとStaffの間だけ変更でき、Adminを付与することもAdminからStaffやNoneへ変更することもできない。

画面では変更できる対象にだけ操作を表示する。実行者に許可されたロールを選び、「変更する」で保存する。権限を剥奪する場合はNoneを選ぶ。保存が完了すると対象者と変更後のロールを表示する。失敗時は成功扱いにせず、権限と通信状況の確認を案内する。一覧取得は再試行できる。

一覧取得とロール変更のエラーは赤、変更成功は緑の通知欄で表示する。いずれも閉じるボタンで非表示にできる。通知を閉じてもロールは変わらず、エラーを閉じることは再試行を意味しない。

Ownerのロールは変更できない。剥奪の対象にもならない。

自分自身のロールも変更できない。誤操作で自分が業務を操作できなくなることを防ぐため、Adminの変更はOwner、Staffの変更はOwnerまたはAdminが行う。

ロールを変更すると、対象の利用者が次に操作した時点から新しいロールが適用される。

### 受け入れ例

1. Noneの利用者へStaffを付与する。
2. 対象の利用者が業務画面を利用できるようになる。
3. Staffを剥奪すると、対象の利用者は公開ページ以外を利用できなくなる。
4. Ownerのロールを変更する操作は成立しない。
5. 自分自身のロールを変更する操作は成立しない。
6. AdminによるNone・StaffからAdminへの変更、およびAdminからStaff・Noneへの変更は成立しない。Ownerによる同じ変更は成立する。
7. 変更の確認後に対象者がAdminへ昇格した場合も、Adminによる変更は保存時に拒否される。

## SPEC-SYS-009 スタッフ画面を最新状態へ同期する

関連要件: `REQ-SYS-004`、`REQ-SYS-006`

注文・調理・受け渡し画面は、D1を唯一の正本とする。認証・認可されたHTTP APIで保存が成功した後、出店共通のDurable ObjectからWebSocketで変更対象とリビジョンを通知する。通知には注文明細、在庫残数、スタッフ情報を含めず、画面上の通知メッセージにも使わない。端末は必要なデータをAPIから再取得する。

| 対象画面   | 照合範囲                   | 再取得するデータ                 |
| ---------- | -------------------------- | -------------------------------- |
| 注文・会計 | 在庫・スタッフ向けメニュー | 商品一覧と在庫残数               |
| 調理       | 注文状態                   | 日本時間の当日の未取消注文と明細 |
| 受け渡し   | 注文状態                   | 日本時間の当日の未取消注文と明細 |

リビジョンの照合には、注文・会計画面が`GET /staff/menu/revision`、調理・受け渡し画面が`GET /staff/orders/revision`を使う。いずれもStaff以上の権限を必要とし、`{ revision }`を返す。通知接続は`GET /staff/events`を使う。

リビジョンは対象データと同じトランザクションで更新する。取得結果にも、そのデータと同じ読み取り時点のリビジョンを含める。取得中に新しい通知を受けた場合は、必要なら取得完了後に再取得し、古い結果で新しい通知を消さない。重複・順序が逆の通知は業務操作の再実行につなげない。

WebSocketの接続状態にかかわらず、前景画面は30秒ごとにAPIでリビジョンを照合する。変化がなければ一覧を再取得しない。接続確立・再接続・画面復帰・通信復帰時は定期照合を待たずに取得する。調理・受け渡しは照合時にも営業日を確認し、日本時間の0時を過ぎたら当日の一覧へ切り替える。画面休止中のタイマー実行は保証しない。

WebSocketだけが切れた場合は自動再接続中であることを表示し、HTTPによる照合と業務操作を継続する。初回のデータを取得できていない場合とHTTP取得・照合に失敗した場合は、入力を保持して新しい確定・状態変更を止める。バックグラウンド再取得中であることだけを理由に操作を止めない。取得が回復したら操作を再開できる。注文確定の結果不明時は[`SPEC-SAL-005`](sales.md#spec-sal-005-注文を一度だけ確定する)に従い、同じ要求識別子で結果を確認する。

スタッフ接続ではセッション、現在のStaff以上の権限、スタッフ画面のOriginを検証する。通知の送信前にもセッションと現在の権限を確認し、失効した接続には変更通知を送らず切断する。再取得APIも毎回認可し、権限失効を確認した画面はスタッフデータの表示と取得を停止する。公開側には接続経路を提供しない。

D1の保存後に通知が失敗した場合は、通知失敗を記録する。保存済みの業務操作は成功として返し、通知の失敗を理由に再実行しない。

### 受け入れ例

1. 別端末で注文を確定すると、会計の在庫残数と調理・受け渡しの注文一覧が更新される。調理・受け渡しの状態変更も別端末に反映される。
2. データが変わらなければ、定期照合で一覧の再取得や入力の消失が起こらない。
3. 保存後の通知を失敗させても、接続したままの全端末が次の照合と取得で追いつく。
4. 取得中の変更、重複通知、切断、画面休止から回復し、古い表示が固定されない。
5. 権限剥奪・ログアウト・セッション期限切れの後は、その接続へスタッフの変更通知を送らず、APIもスタッフデータを返さない。
6. 試験用の保存処理で取消と在庫復元を行うと、照合で取消済み注文が対象から外れ、在庫残数が更新される。
