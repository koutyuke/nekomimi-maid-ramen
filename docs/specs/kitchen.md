# 調理仕様

## 結論と対象範囲

調理担当者は、当日の確定注文に含まれるmainとサイドを担当し、商品ごとに調理状況を更新する。ドリンクは受け渡し担当者が準備するため、調理画面には表示しない。

調理画面の「対応済み」は、選択中の担当範囲がすべて完成したことを示す一時的な表示状態である。注文の完成や受け渡し済みとは異なり、保存しない。

## 画面と一覧

Staff以上の担当者はスタッフのトップから「調理」を選び、`/kitchen`を開く。画面は現在時刻から日本時間の営業日を自動で求め、その日の未取消注文だけを取得する。営業日の入力欄は設けず、画面を開いたまま日本時間の0時を過ぎた場合は新しい営業日の一覧へ切り替える。

カード表示領域の上に、次の選択肢を持つ担当範囲フィルターを置く。

- すべて表示（main・サイド）
- main（ラーメン）のみ
- サイドのみ

初期値は「すべて表示」とし、選択は保存しない。フィルターは注文カードと商品行の両方へ適用する。選択中の分類を含まない注文はカードごと表示せず、ドリンクだけの注文はどの選択でも表示しない。

注文は1件ずつカードにし、画面幅に応じて1列または2列で表示する。カード上部には注文番号と、選択中の商品から算出した対応状況を表示する。商品行は商品名、数量、明細の調理状況、操作ボタンを一つの枠内にまとめ、商品の境界を明確にする。

| 選択中の商品の組み合わせ | カードの対応状況 |
| ------------------------ | ---------------- |
| すべて未調理             | 未調理           |
| すべて完成               | 対応済み         |
| それ以外                 | 調理中           |

「それ以外」には、調理中の商品がある場合と、未調理と完成が混在する場合を含む。カードの対応状況は表示のたびに選択中の商品から算出し、保存しない。フィルターを変更した場合は、新しい担当範囲で再計算する。ドリンクを含む注文全体の調理状況はカード上部へ併記しない。

「対応済みを非表示」は担当範囲フィルターと分けたチェックボックスとし、初期値をオンにする。オンの場合は、選択中の商品がすべて完成した注文カードを非表示にする。商品行だけを隠すことはしない。チェック状態は保存しない。

注文カードは、調理中、未調理、対応済みの順に並べる。同じ対応状況では注文番号の小さい順に並べる。

## 調理状況の管理

| 明細の調理状況 | 意味                                         |
| -------------- | -------------------------------------------- |
| 未調理         | 確定した直後の状態。まだ誰も引き受けていない |
| 調理中         | 調理担当者が明細全体を引き受けた状態         |
| 完成           | 明細に含まれる全数量の準備ができた状態       |

同じ商品の数量は一つの明細にまとめ、その全数量を一括で扱う。調理状況は`order_lines.cooking_state`へ保存する。担当者は記録せず、権限を持つ他のスタッフも更新できる。ドリンクも同じ3状態を使うが、更新は[受け渡し画面](handoff.md)で行う。

| 明細の組み合わせ | 注文全体の調理状況 |
| ---------------- | ------------------ |
| 全明細が未調理   | 未調理             |
| 全明細が完成     | 完成               |
| それ以外         | 調理中             |

注文全体の調理状況は保存も直接更新もせず、全明細から算出する。「ラーメンは完成、餃子は未調理」も注文全体では調理中となる。全明細が完成した場合だけ受け渡し可能となる。これは調理画面のフィルターに応じた「対応済み」とは別の判定である。

完成した明細は操作できない。受け渡し済みの注文を表示する場合は、その旨を示し、更新操作を提供しない。

確定、明細の調理状況、受け渡しの変更は自動で反映する。読み込み中、注文なし、取得失敗を区別する。通信が途切れた場合は自動再接続中であることを表示し、最新情報を確認できるまで更新操作を無効にする。「再読み込み」でも現在の一覧を取得できる。

## SPEC-KIT-001 当日の担当商品を優先順に表示する

関連要件: `REQ-KIT-001`、`REQ-SAL-005`

調理画面には、当日の未取消注文に含まれるmainとサイドだけを表示する。注文候補、確定に失敗した内容、別営業日の注文、取消済みの注文、ドリンクだけの注文は表示しない。

### 受け入れ例

1. 当日のmain・サイド・ドリンクを含む注文、ドリンクだけの注文、取消済みの注文、前日の注文を用意する。
2. 調理画面を開くと「すべて表示」が選択され、「対応済みを非表示」がオンになっている。
3. 当日の未取消注文のmainとサイドだけが、1注文1カード、1商品1枠で表示される。ドリンクだけの注文、取消済みの注文、前日の注文は表示されない。
4. mainだけを選ぶと、mainを含むカードとmainの商品行だけが表示され、各カードの対応状況がmainだけから再計算される。
5. 選択中の商品がすべて完成するとカードが非表示になり、「対応済みを非表示」をオフにすると対応済みとして表示される。
6. 調理中、未調理、対応済みの順に並び、同じ対応状況では注文番号の小さい順に並ぶ。

## SPEC-KIT-002 明細ごとの調理状況を許可された順序で更新する

関連要件: `REQ-KIT-002`、`REQ-HAND-001`

調理画面はmainとサイドにだけ更新操作を提供する。明細の調理状況は未調理から調理中へ、調理中から完成へ進める。着手を取り消す場合に限り、調理中から未調理へ戻せる。完成から前の状態へは戻せず、未調理から完成へ飛ばせない。状態の変更で明細の数量、価格、在庫は変更しない。

サーバーは明細の現在の調理状況を読み出し、変更先への遷移が許可されている場合だけ更新する。読み出し後に同じ明細が変更され、保存時の状態が読み出した状態と一致しない場合は更新を拒否する。同じ注文でも別明細への更新は独立して成立する。競合時は最新の一覧を取得して再確認を案内する。通信失敗で結果が分からない場合も成功扱いにせず、一覧を読み直してから操作する。

サーバーは保存と同時に、明細の状態、注文が未取消・未受け渡しであること、担当者の現在の権限を確認する。取り消し済みの注文は調理画面に表示せず、調理状況を更新できない。

### 受け入れ例

1. ラーメン2杯、サイド1品、ドリンク1杯の注文を確定する。
2. 調理画面ではラーメンとサイドにだけ更新操作が表示され、ドリンクは表示されない。
3. ラーメンを未調理から調理中、完成へ進め、サイドを調理中から未調理へ戻せる。
4. 完成から戻す操作と、未調理から完成へ飛ばす操作は成立しない。
5. 同じ明細への同時着手は一方だけ成立し、別明細への同時着手は両方成立する。
6. 取消済み、受け渡し済み、または保存前に権限を失った担当者からの更新は成立しない。

## API

| 操作                       | 経路                                                |
| -------------------------- | --------------------------------------------------- |
| 当日の注文と明細を取得する | `GET /orders?businessDate=:businessDate`            |
| 明細の状態を更新する       | `PATCH /orders/:id/lines/:menuItemId/cooking-state` |
| 変更を通知する             | `GET /orders/events`                                |

一覧要求は日本時間の現在日を`businessDate`へ指定する。応答の各明細は、画面が担当範囲を判定できるよう商品分類を含む。

更新要求は変更先の`to`だけを持つ。サーバーは読み出した変更元を更新条件へ含める。状態、取消、受け渡し、保存時の権限の条件が成立しない場合は`409`を返す。通知を受けた画面は現在の営業日を指定して一覧を再取得する。
