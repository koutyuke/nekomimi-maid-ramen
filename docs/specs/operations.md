# 運用仕様

## 現在の状態

開店前、営業中、閉店後に確認する対象は定まっているが、担当者、頻度、判断基準、障害時の代替手順は未決である。この仕様だけでは当日の手順として実行できない。

開催条件と業務量は[`Q-OPS-002`](../meta/questions/Q-OPS-002-event-conditions-and-load.md)、障害時の切り替えと復旧は[`Q-OPS-001`](../meta/questions/Q-OPS-001-fallback-operation.md)、データ保持と終了処理は[`Q-OPS-003`](../meta/questions/Q-OPS-003-data-retention.md)、当日の担当者と判定基準は[`Q-OPS-004`](../meta/questions/Q-OPS-004-operating-responsibilities.md)で決定する。

## SPEC-OPS-001 開店前に業務全体を確認する

関連要件: `REQ-OPS-001`

営業開始前に、次を本番内容と実物に照らして確認する。

| 確認対象                                           | 完了条件                                     |
| -------------------------------------------------- | -------------------------------------------- |
| 出店場所、営業時間、メニュー、価格、スポンサー情報 | 公開画面と承認済みの内容が一致している       |
| 各商品の説明と特定原材料                           | 使用する材料の原材料表示と一致している       |
| 商品ごとの初期在庫                                 | 実在庫とシステム上の在庫が一致している       |
| 会計、調理、受け渡し端末                           | 各役割で主要操作を一回完了できる             |
| 注文から受け渡しまで                               | 注文、在庫、各画面の状態が一致する           |
| 障害時の代替手段                                   | 全担当者が切り替え条件と保管場所を説明できる |

担当者と実施時刻は`Q-OPS-004`で決定する。

### 受け入れ例

1. 本番相当のデータ、役割、端末、ネットワークを用意する。
2. 公開情報と在庫を照合する。
3. 注文入力から受け渡し完了までを一回実施する。
4. 注文、在庫、各画面の状態が一致する。

## SPEC-OPS-002 障害時に重複と不整合を防ぐ

関連要件: `REQ-OPS-002`、`REQ-SYS-002`

通信断、端末故障、電源断、システム停止が発生した場合は、新しい注文確定を安全に停止し、重複注文と在庫不一致を防ぐ代替運用へ切り替える。切り替え条件、責任者、紙などによる受付方法、復旧後の入力と照合は`Q-OPS-001`で決定する。

### 受け入れ例

1. 本番と同じ役割・端末で障害を発生させる。
2. 合意した時間内に代替運用へ切り替える。
3. 復旧後に確定注文、代替受付、実在庫、システム在庫を照合する。
4. 重複注文と在庫不一致が残っていない。

## SPEC-OPS-003 提供可否を判断する

関連要件: `REQ-OPS-003`

開発担当者は、本番利用の可否を、主要画面の存在ではなく次の条件をすべて確認して判断する。

- `PROFILE-INITIAL`に含まれるすべての要件が`accepted`である。
- 対象要件の受け入れ例を本番相当の役割、端末、ネットワーク、業務量で確認し、すべて合格している。
- `PROFILE-INITIAL`の`blocking_questions`が空である。
- 本番データ、役割、端末、ネットワーク、代替運用の準備が完了している。
- 注文、在庫、現金、受け渡しに影響する既知の不具合が残っていない。
- 残る制約と回避手順を当日の担当者が確認している。
- 開発担当者が、受け入れ結果と残るリスクを確認している。

### 受け入れ例

1. `PROFILE-INITIAL`の要件、未決事項、受け入れ結果を確認する。
2. 本番環境と代替運用の準備状況を確認する。
3. 上記条件をすべて満たす場合だけ、本番利用を可と判断する。

## 営業中に確認すること

- 実在庫とシステム在庫の差
- 未処理または長時間停滞した注文
- 端末、通信、電源の状態
- 不正操作または異常な注文

確認頻度、異常と判断する基準、修正権限、連絡先は`Q-OPS-004`で決定する。

## 閉店後に確認すること

- 未完成・未受け渡し注文の扱い
- 実在庫、システム在庫、確定注文、現金の照合
- 翌営業日へ引き継ぐ情報と初期化する情報
- 必要な集計と、不要なデータの削除
- 端末、アカウント、秘密情報、外部サービスの終了
