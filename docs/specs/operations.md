# 運用仕様

## 現在の状態

出店は2026年10月24日と25日の10時から16時まで営業し、注文受付は15時30分に終了する。2日間で来場者3,000人、確定注文400件を想定する。通常時は10分間に6件、ピーク時は10分間に20件の確定注文を見込む。通常時とピーク時は別の10分間を表し、2日間の時間配分は定めない。

スタッフは10人、同時利用する端末は最大7台を想定する。実際の担当者名は各日の開店前にグループチャットで決め、リポジトリには保存しない。運用責任者が離席する場合は、同じグループチャットで代理者を明示して引き継ぐ。

データ保持と終了処理は[`Q-OPS-003`](../meta/questions/Q-OPS-003-data-retention.md)で決定する。

## SPEC-OPS-001 開店前に在庫を確認する

関連要件: `REQ-OPS-001`

Admin権限を持つ担当者は、営業開始前に商品ごとの実在庫とシステム在庫を照合する。差がある場合は、システム在庫を実在庫の数量へ修正する。固定の実施時刻と複数人での確認は設けない。

### 受け入れ例

1. Admin権限を持つ担当者が、商品ごとの実在庫とシステム在庫を照合する。
2. 差がある商品のシステム在庫を実在庫の数量へ修正する。
3. 全商品のシステム在庫が実在庫と一致する。

## SPEC-OPS-002 障害時に重複と不整合を防ぐ

関連要件: `REQ-OPS-002`、`REQ-SYS-002`

1台だけで通信断または端末故障が発生した場合は、別のスマートフォンから同じGoogleアカウントでログインし直す。通信、端末、電源、認証またはシステムの問題により、会計端末2台から注文を確定できず、60秒以内に復旧しない場合は、運用責任者が新しいデジタル注文を停止して紙運用への切り替えを宣言する。運用責任者が不在の場合は会計担当者が宣言する。

結果が届かなかった確定要求は、同じ要求識別子で再送する。紙運用へ切り替える時点でも結果が分からない場合は、代金を返し、その注文を提供しない。復帰前に確定注文を照合し、提供していない注文が成立していた場合はAdmin以上が取り消す。同じ注文を紙で重ねて受け付けたり、来場者から代金を二重に受け取ったりしない。

紙運用中は注文担当と会計担当を分け、受付を一列に集約する。

1. 注文担当が、日ごとに`P-001`から始まる番号、商品、個数を紙の伝票へ記入する。
2. 会計担当が代金を受け取り、伝票へ会計済みの印を付ける。
3. 会計済みの伝票を調理、受け渡しの順に回す。来場者には同じ番号を伝える。
4. 受け渡し後の伝票を残し、販売数の集計に使う。紙の注文をシステムへ個別に入力し直さない。

紙運用中は在庫表を作らない。商品がなくなった場合は調理担当者がグループチャットで知らせ、注文担当がその商品の受付を止める。

デジタル運用へ戻す前に、Admin権限を持つ担当者が結果不明だった注文を照合し、実在庫を数えてシステム在庫を現在数へ修正する。会計端末2台から接続できることを確認した後、運用責任者が復帰を宣言する。在庫を修正できない場合は、その日の営業終了まで紙運用を続ける。

### 受け入れ例

1. 確定は成立したが結果を受信できない注文を発生させ、会計端末2台を利用不能にする。
2. 60秒後に紙運用へ切り替え、結果不明の注文は返金して提供しない。
3. 別の注文について、紙の伝票で注文、会計、調理、受け渡しを完了する。
4. 復旧後、結果不明だった確定注文を取り消し、実在庫に合わせてシステム在庫を修正する。
5. 会計端末2台から接続できることを確認し、デジタル運用へ戻る。
6. 同じ注文の二重確定と二重会計がなく、提供していない注文が残らず、システム在庫が実在庫と一致している。

## SPEC-OPS-003 提供可否を判断する

関連要件: `REQ-OPS-003`

開発担当者は、本番利用の可否を、主要画面の存在ではなく次の条件をすべて確認して判断する。

- `PROFILE-INITIAL`に含まれるすべての要件が`accepted`である。
- 対象要件の受け入れ例を本番相当の役割、端末、ネットワーク、業務量で確認し、すべて合格している。
- `PROFILE-INITIAL`の`blocking_questions`が空である。
- 本番データ、役割、端末、ネットワーク、代替運用の準備が完了している。
- 注文、在庫、現金、受け渡しに影響する既知の不具合が残っていない。
- 残る制約と回避手順を当日の担当者が確認している。
- 開発担当者が、受け入れ結果と残るリスクを確認している。

### 受け入れ例

1. `PROFILE-INITIAL`の要件、未決事項、受け入れ結果を確認する。
2. 本番環境と代替運用の準備状況を確認する。
3. 上記条件をすべて満たす場合だけ、本番利用を可と判断する。

## 営業中に確認すること

定期巡回は行わない。次の状態を見つけた担当者は、グループチャットへ報告する。

- 注文確定が会計端末2台で失敗し、60秒以内に復旧しない。
- 未完成の明細が15分以上同じ調理状態のまま更新されない。
- 実在庫とシステム在庫に差がある。
- 現金と、確定注文および紙伝票を合計した売上に差がある。
- 認証または権限のない操作が一件でも成立する。

運用責任者は報告を確認して対応を指示する。在庫と注文の修正はAdmin以上、システムと認証の調査は開発担当者が行う。初期提供範囲では、固定の締め作業とシステム固有の閉店後確認を設けない。閉店後に差異や未完了注文を見つけた場合も、同じグループチャットへ報告する。
