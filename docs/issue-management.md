# Issue の起票

Issue は、読んだ人が「なぜ必要か」「どこまで扱うか」「何を確認すれば完了か」を判断できる内容にする。問題、対応範囲、完了条件を整理してから、[テンプレート](#テンプレートを選ぶ)とラベルを選び、[GitHub で起票する](#起票する)。

## タイトルと作業の単位

タイトルは、対象と問題または達成したい結果が分かる形にする。不具合なら「在庫が0個の商品を注文確定できてしまう」、改善なら「在庫不足で注文を確定した際に、画面へ理由を表示する」のように書く。「在庫の修正」だけでは、何を直すか判断できない。

通常の Issue は、完了を一つのまとまりとして判断できる範囲にする。画面、API、仕様の変更が同じ結果を実現するために必要なら、一つの Issue で扱ってよい。別々に完了できる作業が複数ある場合は Issue を分け、全体の追跡が必要なら `T-Epic` で束ねる。ブランチとプルリクエストの分け方は[変更管理](change-management.md)に従う。

たとえば「在庫不足の注文を拒否し、画面へ理由を表示する」は一つの結果として扱える。一方、「在庫不足の拒否」と「メニューの写真追加」は別々に完了できるため、Issue を分ける。

## 本文をどのような内容にするか

### 問題と必要性を書く

誰が、どの操作や作業で、何に困っているかを書く。現状の不都合と、解決したときにできることをつなげる。機能の提案なら利用者の場面、開発作業なら保守・検証・運用への影響を示す。

たとえば「エラー表示を改善する」だけでなく、「会計担当者が在庫不足で注文を確定できなかったとき、理由が表示されず、個数の修正が必要だと判断できない」と書く。これは書き方の例であり、確認済みの不具合を示すものではない。

観測した事実、原因の推測、解決案は区別する。「成功応答が返った」は事実として書けるが、保存状態を見ていなければ「注文が保存された」とは断定しない。解決案がある場合は、その案で問題を解消できると考える理由を添える。原因や実装方法が未判明でも、問題を報告できる。

### 対応範囲を絞る

この Issue で実現する結果と、影響する操作や業務を示す。調査済みなら変更する画面、API、文書も記載する。関連して見える別の作業まで含むと誤読される場合だけ、対象外を明記する。

実装手順やファイル一覧だけでは作業の目的が伝わらない。手順を添える場合も、達成したい結果と完了条件を先に書く。途中で独立した問題を見つけたら別の Issue にし、関連リンクを残す。

### 完了を判定できる条件を書く

完了条件は、前提と確認する結果を具体的に書く。一つのチェック項目で一つの結果を判断できるようにし、必要な異常時の動作や、変更してはいけない状態も含める。要件・仕様に受け入れ例があれば参照し、この Issue で確認する範囲を示す。

| 曖昧な記載             | 完了を判断できる記載例                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| 在庫の不具合を直す     | 在庫不足の注文確定要求が拒否され、注文が保存されず、在庫も変化しない                                           |
| テストを追加する       | 在庫不足の注文が保存される不具合を検出できる回帰テストがある                                                   |
| 起票ドキュメントを書く | 起票者が種別ラベルを選び、対応範囲と完了条件を書けるよう、判断基準と例が記載されている                         |
| リファクタリングする   | 対象の重複した在庫判定を一か所へ集約し、既存の受け入れ例で注文確定と在庫更新の結果が変わらないことを確認できる |

### 種別に応じた根拠を添える

| 内容                     | 読み手の判断に必要な情報                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| 不具合                   | 再現手順、期待と実際の結果、環境・版・頻度。再現できない場合も、分かっている発生条件と未確認事項を示す |
| 新機能・改善             | 誰がいつ使うか、現状の不都合、実現したい利用の流れ。提案段階の内容は提案と明記する                     |
| リファクタリング・テスト | 現在の保守上の問題や防ぎたい不具合、改善する範囲、維持する挙動と確認方法                               |
| 文書・設定・依存更新     | 対象の文書や設定、必要な理由、変更の影響、正しくなったことの確認方法                                   |
| Epic                     | 全体で達成する結果と範囲、子 Issue の役割とリンク、子の結果を合わせた完了条件                          |

関連情報には、根拠になる要件・仕様の節、再現に必要なログや画像、依存する Issue を載せる。文書全体や会話履歴を貼るだけにせず、今回の判断に必要な箇所と、その情報が何を裏付けるかを示す。秘密情報や個人情報は除く。

### 分からないことと着手条件を示す

未確認の項目を推測で埋めず、何が分かれば作業を進められるかを書く。たとえば「判断待ち」だけでなく、対象の `Q-*` へリンクし、「障害時に紙へ切り替える条件の決定を待っている」のように必要な判断を示す。

調査そのものを作業にする場合は、調べる問いと判断に必要な成果物を完了条件にする。「調査する」だけでなく、「失敗応答時に注文・在庫が変更されるかを確認し、再現条件と結果を記録する」のように書く。関連する文書がなければ「該当なし」とし、仕様の決定が必要なら[ドキュメント管理](documentation-management.md)に従って未決事項へつなげる。

## テンプレートを選ぶ

本文のひな形は [`.github/ISSUE_TEMPLATE/`](../.github/ISSUE_TEMPLATE/) で管理する。

| テンプレート                                            | 用途                                                                                                   | 種別ラベル                         |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ---------------------------------- |
| [不具合の報告](../.github/ISSUE_TEMPLATE/bug-report.md) | 期待する動作と実際の動作の違いを報告する。原因や修正箇所が分からなくても、観測できた事実から起票できる | `T-Bug` を自動付与                 |
| [作業・機能の提案](../.github/ISSUE_TEMPLATE/task.md)   | 新機能、改善、リファクタリング、テスト、文書、設定の作業を提案する                                     | 主な成果物に応じて `T-*` を1つ選ぶ |
| [大項目（Epic）](../.github/ISSUE_TEMPLATE/epic.md)     | 複数の Issue を束ねて、全体の達成を追跡する                                                            | `T-Epic` を自動付与                |

Epic の子 Issue はそれぞれの成果物に応じた `T-*` を選び、親へのリンクを記載する。親のラベルを子へ一律に付けない。

テンプレートはデフォルトブランチへマージすると起票画面に表示される。設定方法は GitHub 公式の[Issue テンプレートの設定](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository)を参照する。

## ラベルを選ぶ

付与数の規則は[ラベル管理](../.github/labels/README.md)、名称と意味の正本は [`labels.json`](../.github/labels/labels.json)である。次は起票時に迷いやすい選択の目安である。

| 判断すること                               | 選び方                                                                                                                                                                      |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作業の種別                                 | `T-*` を必ず1つ付ける。新機能は `T-Feature`、既存機能の改善は `T-Enhancement`、不具合は `T-Bug` を選ぶ                                                                      |
| 主な成果物が構造・テスト・文書・設定の場合 | 挙動を変えない構造改善は `T-Refactor`、テストが主なら `T-Test`、文書が主なら `T-Documentation`、依存更新や設定は `T-Chore` を選ぶ                                           |
| 複数の成果物がある場合                     | 主となる成果物で種別を1つ選ぶ。不具合修正にテスト追加や文書更新を含めても、種別は `T-Bug` とする                                                                            |
| 変更箇所                                   | `apps/api` は `A-API`、`apps/web` は `A-Web`、`docs/` は `A-Docs`、CI や開発基盤は `A-Infra` を付ける。複数該当ならすべて、未判明なら付けない                               |
| 優先度                                     | 判断済みなら `P-Critical`、`P-High`、`P-Medium`、`P-Low` のいずれか1つを付け、影響や期限を本文に書く。`P-Critical` は最優先・即時対応を要する場合に使う。未判断なら付けない |
| 他の作業や外部要因で着手できない場合       | `X-Blocked` を付け、待っている作業や外部要因、着手できる条件を本文に書く                                                                                                    |
| 未決事項の解決を待つ場合                   | `X-NeedsDecision` を付け、対象の `Q-*` へのリンクと、どの判断が必要かを書く                                                                                                 |

`P-*` は作業の優先度であり、要件TOMLの `must`、`should`、`could` と自動的に対応するものではない。`X-*` は着手を妨げる理由があるときだけ使い、理由が解消したら外す。

## 起票する

1. [Issue 一覧](https://github.com/koutyuke/nekomimi-maid-ramen/issues)で、終了済みも含めて同じ問題がないか検索する。同じ問題があれば、既存の Issue に再現条件や不足情報を追記する。終了済みの問題が再発した場合は、再現状況を追記し、開発担当者へ再開の判断を依頼する。
2. 対象の[要件・仕様](README.md)を確認し、関連する `REQ-*`、`SPEC-*`、`Q-*` へのリンクを用意する。既存の文書に該当するものがなければ、その旨を本文に書く。
3. [New issue](https://github.com/koutyuke/nekomimi-maid-ramen/issues/new/choose)を開き、用途に合うテンプレートを選ぶ。本文の案内を記入内容へ置き換える。タイトルと本文は日本語で書き、未確認の情報は未確認と明記する。
4. Labels から既存のラベルを選ぶ。担当者や対象リリースが決まっている場合は、Assignees と Milestone も設定する。リリースの区切りはマイルストーンで管理する。
5. 完了を判断できる内容になっていることを確認して送信する。作成された Issue で本文、リンク、ラベルを確認する。

既存ラベルの付与にはトリアージ以上の権限が必要である。Labels を操作できない場合は、希望するラベルを本文に書き、開発担当者へ付与を依頼する。ラベルの定義自体を追加・変更する場合は、[ラベル管理](../.github/labels/README.md)に従う。画面操作と権限の詳細は GitHub 公式の[Issue の作成](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/creating-an-issue)と[ラベルの管理](https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels)を参照する。

## 起票後に更新する

調査で変更箇所や影響が分かったら、本文とラベルを更新する。Issue は作業と議論を追跡する場所であり、現在の要件・仕様の正本は `docs/` に置く。未決事項の追加・解決や仕様の変更は、[ドキュメント管理](documentation-management.md)に従って文書へ反映する。Issue の合意やクローズだけでは要件の承認は成立せず、承認は [`DEC-SYS-001`](meta/decisions/DEC-SYS-001-requirement-approval.md)に従う。

対応するプルリクエストから Issue を参照し、完了条件を満たしたことを確認して閉じる。重複で閉じる場合は `duplicate` と重複先、内容の誤りや対象外なら `invalid` と理由、対応しない判断なら `wontfix` と理由を残す。通常の完了時にこれらのラベルは付けない。
