# DEC-SAL-001 注文確定の保存方式

## 結論

注文の保存、注文明細の保存、在庫の減算を、D1のひとつのバッチとして実行する。バッチはひとつのトランザクションとして扱われ、いずれかの文が失敗すると全体が取り消される。

この保存操作は販売領域内部の`OrderConfirmationCommand`ポートへ切り出す。D1の複数の表を一括更新する具象実装は、ユースケース単位の状態変更を担う保存先の実装として`apps/api/src/features/sales/infra/commands/order-confirmation.command.live.ts`に置き、注文確定のユースケースから保存形式を分離する。

### 注文番号の採番

注文を挿入する文の中で、同じ営業日の注文番号の最大値に1を加えた値を求める。番号を先に読んでから書き込む形にはしない。営業日と注文番号の組に一意制約を置き、同時確定で同じ番号が成立しないようにする。

確定に失敗した注文は挿入ごと取り消されるため、欠番は生じない。

営業日は日本時間の暦日とする。開催日そのものは[`Q-OPS-002`](../questions/Q-OPS-002-event-conditions-and-load.md)で決めるが、採番はどの日付であっても同じ規則で動く。

### 二重確定の防止

確定要求には、会計担当者の端末が生成する要求識別子を含める。`orders`の要求識別子に一意制約を置き、同じ識別子の確定を二度成立させない。

確定済みの識別子で確定を求められた場合は、新しい注文を作らず、確定済みの注文をそのまま返す。連打や再送は、応答が届かなかった端末からの再試行であり、確定済みであることを伝えれば会計を続けられる。

### 在庫不足の扱い

在庫不足は、`stocks`の`stocks_quantity_non_negative`が`CHECK`制約違反となる形で現れる。ただし制約違反はどの商品が不足したかを伝えないため、確定の直前に在庫を読み、不足する商品と要求数、残数を業務エラーとして返す。`CHECK`制約は、読み取りから書き込みまでの間に別の確定が在庫を消費した場合に備える最後の防波堤として使う。

読み取りから書き込みまでの間に在庫を奪われた場合は、その時点の在庫を読み直して不足として返す。

在庫の記録がない商品は、残数0の不足として扱う。

### 失敗の見分け方

D1は制約違反を例外の文字列としてしか返さない。在庫不足は`stocks_quantity_non_negative`、二重確定は`orders.request_id`という制約の名前で見分ける。制約の名前を変更すると、この判別が成立しなくなる。

## 理由

D1に対話型のトランザクションがないため、読み取った値を判断してから書き込む形では、判断と書き込みの間に別の確定が割り込む([`DEC-SYS-003`](DEC-SYS-003-technology-stack.md))。注文の保存と在庫の減算をひとつのバッチへ入れ、在庫の下限を制約として表すことで、過剰販売と、注文だけが残る状態の両方を排除できる。

注文番号を単一の文の中で決めるのも同じ理由による。番号を読んでから注文を挿入すると、同じ番号を二つの注文が受け取りうる。

二重確定を要求識別子で防ぐのは、会計担当者の操作の連打と、通信の失敗による端末の再送を、サーバー側で区別できないためである。どちらも「同じ会計をもう一度確定しようとしている」ことに変わりはなく、識別子が同じであれば一度だけ成立させればよい。

不足商品を確定前の読み取りで求めるのは、`CHECK`制約違反が商品を特定しないためである。会計担当者は不足した商品が分からなければ個数を直せない([`SPEC-INV-002`](../../specs/inventory.md))。

## 影響

- `orders`と`order_lines`を`src/core/infra/drizzle/schema.ts`へ追加した。`orders`は営業日と注文番号の組、および要求識別子に一意制約を持つ。
- 注文確定のD1バッチは`apps/api/src/features/sales/infra/commands/order-confirmation.command.live.ts`で`OrderConfirmationCommand`を実装する。販売領域のユースケースはこの契約だけを使い、注文リポジトリは確定済み注文の再読み出しを担当する。
- 注文の確定要求には要求識別子が必須である。画面は確定操作ごとに識別子を生成し、再送では同じ識別子を使う。
- 制約の名前`stocks_quantity_non_negative`と`orders.request_id`は、失敗の判別に使うため変更できない。変更する場合は判別側も同時に変える。
- 在庫不足で確定できなかった場合、応答は不足商品、要求数、残数を含む。
