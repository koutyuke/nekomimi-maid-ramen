# DEC-SYS-001 要件の決定者と承認方法

## 結論

対象範囲、要件、仕様、品質条件、運用、提供可否は、開発担当者が単独で最終決定する。出店責任者を含む他の担当者は、業務内容と当日の運用について情報を提供し、決定内容を確認するが、最終決定は行わない。

決定は、変更内容をプルリクエストとして起案し、開発担当者がマージした時点で確定する。要件TOMLの`status`は、その要件を`accepted`へ変更するプルリクエストをマージした時点で`accepted`になる。`accepted`へ変更できるのは、その要件を参照する未決事項がすべて解決している場合に限る。

## 理由

少人数かつ短期間の出店であり、決定を持ち回ると開催日までに要件を確定できない。単独決定にすることで、要件の競合と変更をその場で解決できる。

マージを承認の記録とするのは、承認した内容と時点をGitの履歴として残し、どの要件をいつ`accepted`にしたかを後から確認できるようにするためである。GitHubでは自身が作成したプルリクエストをレビュー承認できないため、レビュー承認ではなくマージ操作を承認の記録とする。

## 影響

- 提供可否は開発担当者が判断する（`REQ-OPS-003`、`SPEC-OPS-003`）。
- 出店責任者は決定者ではなく、業務情報の提供と決定内容の確認を担う。
- 業務ルールを開発担当者が単独で決めるため、当日の運用と食い違う可能性がある。開店前の確認（`SPEC-OPS-001`）が、その食い違いを検出する最後の機会になる。
