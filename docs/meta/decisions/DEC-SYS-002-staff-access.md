# DEC-SYS-002 スタッフの認証方式とロール

## 結論

スタッフ画面は、学校のGoogleアカウントによるログインで認証する。対象は`gm.ibaraki-ct.ac.jp`ドメインのアカウントに限る。共有パスワードと、ロールとは別の許可リストは使わない。

操作の可否はロールで決まる。初回ログイン時のロールはNoneであり、公開ページ以外を利用できない。

| ロール | 付与方法                                     | 位置づけ                                 |
| ------ | -------------------------------------------- | ---------------------------------------- |
| Owner  | 設定として固定し、画面からは変更できない     | 開発担当者。全操作とロールの付与・剥奪   |
| Admin  | OwnerまたはAdminが付与する                   | 全操作とロールの付与・剥奪               |
| Staff  | OwnerまたはAdminが付与する                   | 定められた業務操作のみ                   |
| None   | 初回ログイン時の初期値                       | 公開ページのみ                           |

各ロールの操作範囲は[システム共通仕様](../../specs/system-wide.md)の`SPEC-SYS-006`で定義する。

## 理由

同じドメインであれば校内の誰でもログインできるため、ログインできることと業務を操作できることを分ける必要がある。初期ロールをNoneにすると、許可した利用者の一覧を別に持たずにロールだけで管理できる。

共有パスワードを採用しないのは、誰が在庫を修正し、誰が注文を取り消したかを記録できないためである。ロールは3段階で足り、利用者ごとの割り当ての管理量は小さい。

Ownerを画面から変更できないようにするのは、ロールの誤操作ですべての管理権限を失う状態を防ぐためである。

ロールを業務役割(会計、調理、受け渡し)と分けるのは、当日のトラブルやシフト変更で担当が入れ替わることが多いためである。業務役割ごとにロールを分けると、担当を替えるたびにロールの変更が必要になる。

## 影響

- スタッフのメールアドレスと表示名を保持する。保持期間と削除は[`Q-OPS-003`](../questions/Q-OPS-003-data-retention.md)で決定する。
- ログインにはGoogleへ到達できる通信が必要である。当日の失敗を避けるため、開店前確認([運用仕様](../../specs/operations.md))で全担当者のログインとロールを確かめる。
- 在庫の修正と、確定した注文の取り消しはAdmin以上に限る。操作内容は[在庫仕様](../../specs/inventory.md)と[注文・会計仕様](../../specs/sales.md)で定義する。
- 権限を誤って失った場合の回復はOwnerが行う。
