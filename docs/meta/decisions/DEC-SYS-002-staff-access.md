# DEC-SYS-002 スタッフの認証方式とロール

## 結論

スタッフ画面は、学校のGoogleアカウントによるログインで認証する。対象は`gm.ibaraki-ct.ac.jp`ドメインのアカウントに限る。共有パスワードと、ロールとは別の許可リストは使わない。

操作の可否はロールで決まる。設定で固定したOwnerを除き、初回ログイン時のロールはNoneであり、業務操作を利用できない。

| ロール | 付与方法                                 | 位置づけ                               |
| ------ | ---------------------------------------- | -------------------------------------- |
| Owner  | 設定として固定し、画面からは変更できない | 開発担当者。全操作とロールの付与・剥奪 |
| Admin  | Ownerが付与する                          | 全業務操作とStaffの付与・剥奪          |
| Staff  | OwnerまたはAdminが付与する               | 定められた業務操作のみ                 |
| None   | 初回ログイン時の初期値                   | 公開ページのみ                         |

各ロールの操作範囲は[システム共通仕様](../../specs/system-wide.md)の`SPEC-SYS-006`で定義する。

## OAuthアプリの構成

要求するスコープは`openid`、`email`、`profile`の3つに限る。認可後の戻り先はAPIの`/auth/google/callback`とし、本番と手元の2つを登録する。プレビュー版のホストは登録しない。

ドメインの判定は、IDトークンの`hd`クレームで行う。認可リクエストの`hd`パラメータは、アカウント選択画面での絞り込みにだけ使う。

GoogleのOAuthアプリは「テスト」状態で運用し、担当者のアカウントをテストユーザーとして登録する。本番公開は[`PLAN-SYS-001`](../plans/PLAN-SYS-001-oauth-app-publishing.md)で扱う。

## 実装と保存

認証とセッション管理はBetter Auth 1.7.3、保存は既存のD1とDrizzle ORMを使う。利用者をGoogleの`sub`で識別し、メールアドレスだけでは既存のアカウントへ結び付けない。[Googleの仕様](https://developers.google.com/identity/openid-connect/openid-connect)はメールアドレスが変更され得るため`sub`による識別を求めている。

Better Authとの接続は`features/system-wide/infra`へ閉じ、経路は同領域の公開するユースケースを通す。ロールの規則は同領域の`domain`、全表の定義は既存どおり`core/infra/drizzle/schema.ts`に置く。利用者とロールを経路へ渡す処理は`routes/auth`が担い、販売などの業務領域は認証ライブラリへ依存しない。

- Googleのコールバックでは、Better Authの`verifyGoogleIdToken`で署名・発行者・宛先・期限を検証してから、`hd`の完全一致とメール確認済みを要求する。`/auth/google/callback`をBetter Auth内部の経路へ接続する。
- `Owner`は`OWNER_EMAIL`で指定した利用者の実効ロールとし、DBのロール列には保存しない。DBへ保存するロールは`Admin`、`Staff`、`None`に限る。
- セッションはAPIホストだけに送信するHttpOnly Cookieで扱う。本番はSecure、SameSite=Laxとする。Cookieへの利用者情報のキャッシュとセッションの自動延長を無効にし、操作ごとにD1の最新ロールを参照する。
- Googleのトークンと端末情報は保存前のフックで除外する。Better Authが要求する対応列はNULLのまま保持する。
- D1では利用者と認証アカウントの登録を一つの対話型トランザクションにできない。途中失敗後は、ロールがNoneで認証アカウントもセッションもない利用者だけ、検証済みGoogleログインで登録を再開する。既存アカウントへのメール一致だけの結び付けは拒否する。

[Better AuthのElysia連携](https://better-auth.com/docs/integrations/elysia)、[Drizzle連携](https://better-auth.com/docs/adapters/drizzle)、[Googleプロバイダー](https://better-auth.com/docs/authentication/google)を参照し、公開パッケージ1.7.3とWorkers上の接続試験で確認した。

## 理由

同じドメインであれば校内の誰でもログインできるため、ログインできることと業務を操作できることを分ける必要がある。初期ロールをNoneにすると、許可した利用者の一覧を別に持たずにロールだけで管理できる。

共有パスワードを採用しないのは、誰が在庫を修正し、誰が注文を取り消したかを記録できないためである。業務の操作権限はNone、Staff、Admin以上の3段階とし、Adminの付与・剥奪だけをOwnerに限定する。

Ownerを画面から変更できないようにするのは、ロールの誤操作ですべての管理権限を失う状態を防ぐためである。Adminの付与・剥奪をOwnerに限定し、Admin同士による管理権限の拡大や剥奪を防ぐ。

ロールを業務役割(会計、調理、受け渡し)と分けるのは、当日のトラブルやシフト変更で担当が入れ替わることが多いためである。業務役割ごとにロールを分けると、担当を替えるたびにロールの変更が必要になる。

IDトークンの`hd`クレームで判定するのは、認可リクエストのパラメータを利用者が書き換えられるためである。`hd`クレームはGoogleの署名の対象であり、改ざんできない。パラメータを判定に使うと、対象ドメイン以外のアカウントがログインできる。

スコープを3つに限るのは、センシティブまたは制限付きのスコープを一つでも要求すると審査の対象となり、担当者へ「確認されていないアプリ」の警告が表示されるためである。利用者の識別には`sub`、所属の判定には`hd`、画面表示にはメールアドレスと表示名を使う。

テスト状態で運用するのは、本番公開にプライバシーポリシーと利用規約の掲載、およびブランド確認が必要なためである。確認に要する期間を出店日までに収められる保証がない。担当者は10人程度であり、テストユーザーの上限100人に対して余裕がある。登録した利用者だけがログインできる状態は、ドメイン判定に加えた明示的な許可として働く。

## 影響

- 保持するプロフィールと認証情報は[`SPEC-SYS-007`](../../specs/system-wide.md)に従う。保持期間と削除は[`Q-OPS-003`](../questions/Q-OPS-003-data-retention.md)で決定する。
- ログインにはGoogleへ到達できる通信が必要である。当日の失敗を避けるため、開店前確認([運用仕様](../../specs/operations.md))で全担当者のログインとロールを確かめる。
- 在庫の修正と、確定した注文の取り消しはAdmin以上に限る。操作内容は[在庫仕様](../../specs/inventory.md)と[注文・会計仕様](../../specs/sales.md)で定義する。
- 権限を誤って失った場合の回復はOwnerが行う。
- 担当者を追加する場合、ロールの付与に加えてGoogle Cloudでのテストユーザー登録が必要になる。開店前確認([運用仕様](../../specs/operations.md))で両方を確かめる。
